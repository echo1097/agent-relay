# V0.1 PRD compliance audit

Baseline: `abea5ba`. The entire PRD, including implementation notes and sections 1 through 61, was read before implementation changes. This initial checklist records source inspection and the passing baseline `go test ./...`; it is not a claim that every real-client acceptance scenario has been exercised. Fixes and final verification will be recorded below without erasing the initial findings.

## Complete

- [x] Sections 1–6: local-first, direct two-node text communication, Go executable, SQLite, HTTP/JSON, provider-independent MCP, no hosted Relay runtime. Polling is the required baseline; event notifications are optional.
- [x] Sections 8–9: configurable port, Tailscale IPv4-only production binding, explicit loopback development exception, `/v1/` routes, persistent UUIDv7 node identity. Evidence: `internal/cli/peers.go`, `internal/config`, `internal/tailscale`, `internal/storage` and binding/identity tests.
- [x] Sections 10–13: distinct session IDs, lightweight metadata, automatic MCP initialization registration, online/busy/idle/offline states, heartbeats, timeout and disconnect. Idle is explicitly caller-controlled, as the PRD's implementation notes allow; automatic idle detection is not required for this release.
- [x] Sections 14–16: Tailscale peer enumeration, bounded hello probing, cache, refresh, last-seen/failure states, compatible hello, local/remote MCP agent discovery and filters. Evidence: `internal/discovery`, `internal/relay/directory.go`, discovery and MCP tests.
- [x] Sections 17–23: message/question/response types, exactly two participants, new conversations and validated follow-ups, unique immutable messages, lifecycle/deadlines, idempotent processing and persistence before acknowledgment. Evidence: `internal/messaging`, `internal/storage/messages.go`, `delivery.go`, migrations, transport and daemon tests.
- [x] Sections 24–27: session-owned durable inbox, unread/pending defaults, caller-supplied answers, derived response route, response linkage and chronological history. Relay never fabricates answers. MCP ignores the illustrative caller-selected inbox ID in favor of the connection's registered identity.
- [x] Sections 28–32: polling, explicit wake-up limitation, useful tool descriptions, all eight required tools, filtered agent metadata and partial status updates. Files remain local under the stricter privacy rules. Evidence: `internal/mcp/server.go`, `internal/relay/session.go`, MCP lifecycle/isolation tests.
- [x] Sections 33–35: unknown/trusted/blocked peers, stable device binding, incoming source verification, outgoing destination verification, trust recheck before persistence, no automatic context export. Evidence: trust tests across storage, transport and daemon; public metadata projection tests. Trust protects messaging, not public discovery endpoints.
- [x] Sections 36–42: migrated SQLite schema, exactly the five required HTTP endpoints, local-only HTTP agent listing, versioned JSON messages/acknowledgments/errors, durable retries and short-lived requests. Wire layouts differ from illustrative JSON examples while preserving required meaning. `/v1/requests` is an example in section 8, not a required endpoint in section 37, so it is correctly absent.
- [x] Section 44: doctor checks version, configuration, storage/migrations/identity, clients, Tailscale, actual listener, discovery and trusted peers, with remediation. Installation mode reports incomplete first-time onboarding separately while retaining real failures.
- [x] Sections 45–47: four compiled Unix targets, OS/CPU detection, HTTPS download, checksum, executable receipt, Tailscale preflight, initialization, login service, supported-client setup, diagnostics, summary, upgrade and uninstall. Defaults require no config edits. Service-specific safety defects are listed below.
- [x] Sections 49–50: small packages separating transport, persistence, MCP and logic; embedded SQLite; existing license. The proposed package tree is illustrative. No need to add empty packages, Windows installer, or authentication framework to match it literally.
- [x] Sections 51–53: bounded worker loops, cancellation, serialized SQLite connections, request draining, offline marking, versioned requests/responses and incompatible-version rejection. MCP is a separate local stdio process, so it can retain queued work while the network daemon is stopped.
- [x] Sections 54 and 60: no network/MCP capability to run shell commands, edit/read arbitrary files, execute Git, start coding agents, install software or run tests. Local service commands and fixed Tailscale CLI calls are setup/network operations, not remote execution. No groups, broadcasts, delegation, context synchronization, model calls, dashboard or central broker.
- [x] Sections 55–56: unit/failure coverage and single automated four-message tests through internal APIs and MCP. They check discovery, question, durable receipt, response, follow-up, second response, ordered retained history, plus duplicate/restart/trust behavior. Baseline full test suite passes.
- [x] Section 59: all implementation phases have code and tests; phases are sequencing guidance, not a reason to retain obsolete restrictions such as “Do not implement MCP yet.”

## Partially complete

- [ ] Sections 7 and 43: `agents` lists only local agents and `status` omits remote agents. Reuse the existing shared directory and retain an explicit local-only option for offline administration.
- [ ] Section 48: most structured lifecycle events exist, but successful Tailscale detection is not logged, disappearing peers do not emit peer-lost events, and MCP explicit offline updates bypass the existing offline event. Add those events without logging message bodies or private metadata.
- [ ] Sections 4, 25, 57, 58 and 61: the transport and MCP path is tested with scripted answers. A live Codex-to-Claude conversation where Claude reasons from its actual coding context has not been verified in this audit. Provide precise real-client steps; do not substitute a scripted reply for proof of model reasoning or invoke metered models without explicit permission.

## Missing

- [ ] Sections 7 and 43: top-level `agent-relay inbox` and `agent-relay conversations` commands. Existing `messages inbox --agent` and `messages history --conversation` cover lower-level access, but do not satisfy the specified human-facing overview commands.

## Incorrect

- [ ] Sections 45 and 59, safe installation: fresh service install accepts and replaces an existing unowned private binary. It also follows a symlink while hashing the destination. Refuse unowned or nonregular private binaries before changing service state.
- [ ] Sections 44–45 and 57, startup verification: `daemonReady` validates hello compatibility but not the expected persistent node identity. Verify the listener against the local saved identity and runtime record before claiming readiness.
- [ ] PRD implementation notes still contain outdated statements that real-tailnet discovery is outstanding and a broken README discovery anchor. Update factual status after verification, without weakening requirements.

## Out of scope but accidentally implemented

None found. Local CLI registration/inspection and named service instances support testing and recovery; they are not remote agent orchestration. Explicit loopback mode is a documented test exception. MCP SDK transitive OAuth code is unused by the stdio integration and does not create hosted authentication. No feature removal is warranted from the inspected implementation.

## Verification boundaries

The existing real-host records cover macOS arm64 on Machine B, macOS amd64 under Rosetta, Linux arm64 and public release installation. This audit will rerun relevant checks on the changed code. No reboot, logout, model-provider call, or change to existing user node identities is implied by those records. GitHub Pages and Releases distribute the executable; they are not runtime message dependencies.

## Additional finding during verification

- [ ] Section 34, incorrect: production discovery GET handlers relied on the listening address alone. Unlike message receipt, they did not verify the connection source against local Tailscale status. Add source verification for health, hello and agent discovery while retaining discovery for unknown tailnet peers. Ignore forwarding headers. This closes a gap for non-tailnet traffic routed to the machine's Tailscale address.

## Known limitations and release decision

- **Decision at audit completion: not yet an unconditional V0.1 release sign-off.** The implementation is a tested release candidate. Complete the real Codex-on-A/Claude-on-B context-based acceptance scenario and publish a new compiled release containing the audited commits before calling the distributed product fully signed off. Existing `v0.1.0` assets were not replaced or retagged.
- An inactive model cannot be awakened portably. Polling while the coding runtime is active is required. Relay never supplies the answer itself. This is the PRD's explicit V0.1 baseline, not missing orchestration.
- MCP reconnection without `--agent-id` creates a new inbox. Resume explicitly to continue an old session; simultaneous sessions must not share an agent ID.
- Production requires Tailscale IPv4. Automatic discovery uses a common configured port. A Tailscale address change requires a service restart. Large tailnets can produce partial discovery within the bounded lookup budget.
- Presence is advisory. Busy and idle are set by callers; no automatic idle inference is implemented.
- Services start at login. Linux before-login/after-logout service persistence requires separately configured lingering. No actual reboot or logout was performed during this audit. macOS amd64 was previously tested under Rosetta; native Intel macOS and a complete Linux amd64 host installer/service flow were not exercised here.
- Logs, databases, old sessions and backups have no automatic retention policy. Keep machine clocks synchronized for cross-machine chronological ordering. Uninstall deliberately preserves data and backups.
- Setup and installation are recoverable sequences, not transactions across binaries, client files, service managers and SQLite. Interrupted partial installs can require manual review. Checksums depend on trust in the GitHub release manifest and are not independent signatures.
- Peer text is untrusted context. Minimal public metadata is filtered, but filtering is not a universal secret detector. Trust applies to a machine, not an isolated process on that machine. Discovery is visible to verified tailnet peers even before message trust.

Exact procedures: [two-computer CLI test](v0.1-acceptance.md#two-computer-cli-test), [Codex on A and Claude Code on B](v0.1-acceptance.md#codex-on-a-and-claude-code-on-b), and [isolated candidate setup](v0.1-acceptance.md#isolated-candidate-setup).
